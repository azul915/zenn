## tl;dr

- LLM を開発・運用に入れるとき、先に決めるのは「何を渡すか」より「何をコードと CI に閉じ込めるか」
- 障害の初期調査、コードレビュー、ナレッジ参照は別領域に見えるが、同じ問いが3回出る。手順が固定なら決定的に実行し、判断だけ LLM に渡す
- 収集クエリを LLM に任せると、同じ障害でも集計の切り口が回ごとに変わる。再現性が先で、省力化はそのあと
- SLO の計装とセキュリティのゲートは、この境界の下敷き。測れないものは、渡す材料も判断基準も作れない

## 散らばって見える作業は、同じ問いの繰り返しだった

Plan → Code → Verify → Release → Operate → Monitor と並べると、手を入れる場所は散らばって見えます。ナレッジの置き場、静的解析、デプロイ前のセキュリティチェック、SLI、障害の初動、改善定例。項目を数えると別々の取り組みです。

中で繰り返しているのは、次の1問です。

**この処理は、入力と手順が固定されていて、出力が毎回同じになるか。**

なるなら、コードと CI とジョブに閉じ込めます。ならないなら、LLM に渡す前に参照材料と観点を揃えます。モデルを増やす話ではありません。

| 領域 | コードと CI に閉じ込める | LLM に渡す |
| --- | --- | --- |
| 障害の初期調査 | 検知、定型クエリ、証拠パッケージ | 過去事例との照合、初期レポート案 |
| コードレビュー | 構文木で判定できる設計制約・規約 | 設計意図、仕様整合、「意図に沿っているか」 |
| ナレッジ参照 | 配置・フォーマット・更新ルール、最小の質問→回答 | 検索基盤そのものより、渡す材料の整備が先 |

3つは連動します。障害調査の証拠、レビューの設計制約と決定記録、ナレッジの規約化された文書は、いずれも LLM の入力です。SLO の計装とセキュリティのポリシー検証は、判断を数値とゲートに落とす側で、境界の下敷きになります。

## 障害調査は、人手で3回やった手順をコードに移す

いちばん具体が揃っているのが、テナント横断のクライアント一斉切断です。

題材にした理由は、機能の重要度ではありません。調査手順が障害調査リポジトリと過去レポートで3回分あり、クエリの落とし穴まで文書化されていたからです。直近1週間で6件、最大でテナント数十・クライアント数百。コンテナの graceful shutdown 未対応が残っており、再発します。縦に1本通す素材として、条件が揃っていました。

パイプラインは次の3段です。

```
[検知]   ログモニター（フィルタ + 閾値）
           例: セッション確立失敗のエラーログが 50件 / 5分 を超える
              ↓ webhook / trigger
[収集]   判断を含まない自動ジョブ
           ・テナント別の内訳
           ・コンテナ基盤のイベント突合（unhealthy / task replaced / draining）
           ・コンピュートの CPU / Memory
           ・セッション中断ログの実害集計
           ・再接続カウント
              ↓ 構造化された証拠パッケージ
[解釈]   LLM（ここだけ）
           ・過去レポートとの照合
           ・同一パターンか逸脱かの判定
           ・初期調査レポート案、チケット文、利用者向け報告文のドラフト
```

収集に落としたのは、人手で3回実施済みの手順そのものです。観測基盤で該当エラーの時間帯と件数を取り、テナント別に割って横断か個別かを見、横断ならクラウド起因と見てオーケストレーションイベントとコンピュートメトリクスを突合し、中断ログで実害を数え、再接続で復旧を確認する。6手順のうち、件数確認のあとの5つは判断を含まないクエリの束なので、コードで書き切ります。

5本を LLM に任せると、同じ障害なのに集計の切り口が回ごとに変わります。過去レポートとの照合と、「今回は既知パターンか、何かが違うか」の判定だけが、解釈の仕事です。

共通の仕組みは1回だけ作ります。トリガー、証拠パッケージを吐くランナー、LLM に渡す口。パターンごとに足すのはデータだけです。検知条件、収集クエリ、照合用の過去レポートと既知の落とし穴。2本目以降は実装を増やしません。

完了条件は、この3段が1パターンで通ることです。再発時、または過去事例のリプレイで、証拠パッケージとレポート案が自動で揃う。起票や通知の自動化、パターン追加、ログ・メトリクス・トレースの数値評価は、そのあとです。

セッション開始の失敗を測る計装は、SLO 側のユーザージャーニーに寄せました。横断障害の初動はこのパイプライン、個別セッションの失敗率は SLI。同じ事象を二箇所で追いません。

:::details 運用メモ — 障害パイプライン
### 人手調査手順（収集ランナーに落とす6手順）

| # | 手順 | データソース | 出力の意味 |
| --- | --- | --- | --- |
| 1 | 該当エラーの時間帯・件数 | 観測基盤ログ API | インシデント窓の確定 |
| 2 | テナント別内訳 | 同上 | 複数テナントなら横断、単一なら個別 |
| 3 | オーケストレーションイベント突合 | クラウド API | unhealthy / task replaced / draining |
| 4 | コンピュート CPU / Memory | 観測基盤メトリクス API | リソース起因の除外 |
| 5 | セッション中断ログ集計 | ログ API | 実害（中断理由付き） |
| 6 | 再接続カウント | ログ API | 復旧の確認 |

#1 は検知で済ませる。#2〜6 が「5本のクエリ」で、LLM に渡さない。

### 検知条件（暫定）

- ログフィルタ: セッション確立失敗を示すエラーメッセージ（抽象化前は購読未実行系）
- 閾値: **50件 / 5分**（暫定。ベースライン取得後に見直す）
- トリガー: モニター → webhook → 収集ランナー起動

### 証拠パッケージ（出力契約のたたき台）

ランナーは JSON を1ファイルにまとめる。LLM 入力も人間の初動確認も、この形を前提にする。

```json
{
  "pattern_id": "tenant-wide-client-disconnect",
  "triggered_at": "2026-07-29T12:34:56Z",
  "window": { "from": "...", "to": "..." },
  "error_summary": { "count": 312, "message_filter": "..." },
  "tenant_breakdown": [{ "tenant_id": "...", "count": 42 }],
  "orchestration_events": [{ "type": "task replaced", "at": "..." }],
  "compute_metrics": { "cpu_max": 0.82, "memory_max": 0.71 },
  "session_interruptions": { "count": 18, "by_reason": { "...": 12 } },
  "reconnect_counts": { "count": 290, "window_minutes": 30 },
  "known_pitfalls": ["tenant_id の正規化（大文字小文字）"]
}
```

`known_pitfalls` はパターン固有データ。過去調査で踏んだ落とし穴を毎回添える。

### 再発時のオンコール（人間がまだやること）

1. モニター通知 → 数分以内に `evidence.json`（または同等）が届くのを待つ
2. `tenant_breakdown` で横断かどうかを確認（ここまで自動）
3. 横断 + orchestration_events が task replaced 系なら、過去レポートの「既知パターン」候補として扱う
4. LLM レポート案は照合と文案のたたき台。ファクトは JSON のみを正とする
5. まだやらない: 手元で同じクエリを打ち直す（パッケージを無視しない）

### 層ごとの完了条件

| 層 | 完了の目安 |
| --- | --- |
| 検知 | 閾値超過でトリガーが発火する |
| 収集 | 5種クエリ実行 → 構造化パッケージ出力 |
| 解釈 | 過去レポートと照合しレポート案生成（1回以上試行） |
| 全体 | 再発時（または過去事例リプレイ）でパッケージ + レポート案が自動で揃う |

### ランナーの置き場（未決）

- Lambda（webhook 直結、短時間バッチ向き）
- コンテナ RunTask（API 呼び出しが多い場合）
- GitHub Actions `workflow_dispatch`（障害調査リポジトリと同居させる場合）

共通の仕組みは1回だけ。2パターン目以降は `pattern_id` とクエリ定義を足す。

### 抽象化前の参照（自分用）

- 障害調査リポジトリ `troubleshoot/report/` の確定レポート 3件分
- 収集ランナーの土台: `troubleshoot/tools/datadog` 等
:::

## コードレビューでも、構文木で決まるものは CI に入れる

LLM で設計・実装・改修が速くなると、品質の穴も増えます。アーキテクチャ逸脱、既存仕様との不整合、レビュー品質のばらつき。障害調査と同じ問いを、レビューに持ち込みます。

振り分けの軸は、構文木で決まるかどうかです。見れば違反と分かる設計制約とコーディング規約はリンターにします。設計意図、仕様整合、セキュリティのうち「この変更は意図に沿っているか」は LLM レビューに残します。

静的側では、散発していたチーム固有リンターを棚卸しし、対象課題・カバレッジ・置き場所をルールカタログに載せました。実装・テスト・CI 統合の共通規約を1セット書き、規約どおりにルールを1種以上 CI へ入れます。カタログの未カバー領域を計画的に潰す運用は、そのあとです。

判断側は、特定のレビューフロー1件を題材にします。LLM に渡すコンテキスト（アーキテクチャルール、設計制約、決定記録）を先に揃え、そのフローで指摘の質を定性評価する。指摘の検証から修正までを自動で回す枠、適用範囲の拡大、定量評価は、そのあとです。

障害調査では「クエリはコード、照合は LLM」でした。ここでは「構文木で決まるものは CI、意図の判定は LLM」になります。対象は違います。線の引き方は同じです。

:::details 運用メモ — レビュー基盤
### ルールカタログに載せる項目

| 項目 | 例 |
| --- | --- |
| ルール ID | `no-direct-fetch-in-component` |
| 対象課題 | アーキテクチャ逸脱、層の逆転 |
| カバレッジ | 対象ディレクトリ / ファイル種別 |
| 置き場所 | リポジトリ、CI ジョブ名 |
| テスト | 正例・反例の fixture |

### 今期の完了条件

- 共通規約（実装・テスト・CI 統合手順）を1セット文書化
- 規約どおりにルール 1種以上を CI へ統合し、失敗時の見え方を確認
- LLM レビュー試行 1フロー（題材 PR の種類を固定）＋定性評価メモ

### LLM に渡すコンテキスト（レビュー試行用）

- アーキテクチャルール（ディレクトリ責務）
- 設計制約（禁止パターン一覧）
- 決定記録（なぜそうなったか。ADR 相当）
:::

## ナレッジは、検索基盤より先に置く場所を決める

ナレッジ側で先に作るのは、文書を検索してから回答を生成する構成ではありません。知識を置く場所、フォーマット、メタデータ、更新ルールです。将来ドメインを足すときに、規約どおりデータを足すだけで済む状態にします。

最初の1ドメイン（プラットフォームの主要機能仕様）をその規約で整えます。ベクトル検索は使いません。用意したコンテキストとプロンプトテンプレートで、「質問 → 参照 → 回答」を1本通します。チーム内で1サイクル回し、回答の精度と欠けている知識を拾って規約を直す。効果の高かった使い方を2〜3件、標準フローとして文書化します。

ここでも主役は、LLM に渡す前の作業です。検索基盤を先に立てると、腐った材料を大量に検索できるだけになります。`docs` に生成物が溜まり、渡すたびにコンテキストの信頼が落ちる問題は、ナレッジ規約と、後述の改善定例で扱います。

:::details 運用メモ — ナレッジ
### 規約で先に決める項目

- **配置**: どのディレクトリに何を置くか（仕様 / runbook / 決定記録）
- **フォーマット**: 見出し階層、メタデータ（更新日、所有者、対象ドメイン）
- **更新ルール**: 誰がいつ直すか。生成物の扱い（要約して統合するか、削除するか）

### 最小の質問→回答（ベクトル検索なし）

1. 質問
2. 用意したコンテキスト（1ドメイン分）をプロンプトに注入
3. 回答 → 精度と欠落を記録
4. 規約またはコーパスを修正

### 今期の完了条件

- 1ドメイン（主要機能仕様）を規約どおり整備
- チーム内 1サイクル試行
- 効果の高かった使い方 2〜3件を標準フローとして文書化
:::

## SLO とセキュリティは、境界の下敷きを先に測る

LLM の境界だけを語ると、計測とゲートが浮いて見えます。どちらも、判断を数値とポリシーに置く作業です。

SLO 側では、P0 ユーザージャーニー3本（待機監視、セッション開始、セッション継続）の SLI を定義し、計測ログとイベントを実装し、暫定集計でベースラインを取ります。種類は4つです。待機中のメディア到達、開始の成功率、開始の双方向確立、継続の1分集約。許容失敗量を予算としてリリース可否を決める運用は、実測分布がないと設定できません。今は測れる状態までです。

セキュリティ側では、要件を検証できるポリシーとしてコード化し、CI/CD にスキャンとポリシー検証を載せます。パイロット1システムに絞り、Critical/High の対応期限（目標5営業日以内）を定義して計測を始める。手動承認に依存していた変更フローを1つ以上自動化します。

どちらも、LLM に渡す材料と、LLM が支援する判断の前提を作る作業です。エラーバジェットでリリースを止める、運用結果を見てルールを直す、は境界が固まってからの話になります。

:::details 運用メモ — SLI 計装
### P0 ユーザージャーニーと SLI

| ジャーニー | SLI ID（例） | 測るもの | 今期 |
| --- | --- | --- | --- |
| 待機監視 | 2A | 待機中のメディア到達 | 計装 + ベースライン |
| セッション開始 | 3A | 開始成功率 | 計装 + ベースライン |
| セッション開始 | 3B | 開始の双方向確立 | 計装 + ベースライン |
| セッション継続 | 4A | 1分集約の継続品質 | 計装 + ベースライン |

実装順: 開始（3）→ 継続（4）→ 待機（2）。SLO 数値合意・エラーバジェット運用・リリース判断への接続は次期。

### 今期の完了条件

1. SLI 定義の文書化（上表）
2. 計測ログ・イベントの実装
3. 暫定集計でベースライン初回取得 + 過去インシデントで机上検証 1回

### 障害パイプラインとの分担

- 横断切断 → 検知・収集・解釈パイプライン（本記事の主例）
- 個別セッション開始失敗 → SLI 3A/3B（同じ失敗を二重に追わない）
:::

:::details 運用メモ — セキュリティゲート
### 今期スコープ

- パイロット 1システム
- ポリシー 1種以上を検証可能な形式でコード化
- CI/CD にスキャン + ポリシー検証を載せる
- Critical/High の対応期限: 目標 5営業日以内（計測開始）
- 手動承認依存の変更フロー 1つ以上自動化

### 自動化候補

- 依存関係更新 PR の自動マージ（条件付き）
- IaC lint ゲート
- デプロイ前スキャン

### 次期

- 運用結果からルール改善
- 主要システム全体への展開

## 面を埋める前に、境界を1か所で完成させる

複数テーマを「主要システム100%」「三本柱100%」のように面で埋めようとすると、Observability・品質・セキュリティ・ナレッジが同時に互いの成果物を前提にします。SLI の計装がユーザージャーニー1本の途中なのに、エラーバジェットでリリースを止める約束が同じ期間に乗る、という状態になります。

採ったのは、1障害パターン・1レビューフロー・1ナレッジドメインを端から端まで通してから、横に足す進め方です。カバレッジを減らす話ではありません。境界の設計を1か所で完成させ、他の領域へ写すための手段です。

改善定例も同じ型に寄せました。発散 → 収束 → 実行 → 検証。各回の必須アウトプットは決定事項・オーナー・期限。実行フェーズの仕掛りは1本まで。横断の LLM 施策（自動化、開発プロセス、レビュー、ナレッジ）の優先度と効果を、同じループで見ます。

## 効いているかは、使い方を増やす前に見る

境界を引いたあと、見る点は次です。

再発時に、証拠パッケージとレポート案が自動で揃ったか。揃ったとして、人間がパッケージを無視して手元でクエリを打ち直していないか。

レビュー側では、構文木で閉じたルールが CI で実際に逸脱を止めているか。LLM レビューの指摘が、人間の見落としを埋めているか、ノイズだけ増えているか。

再現性が崩れているなら、渡す範囲を狭めます。保たれているなら、次のパターンへデータを足します。使い方を増やすのは、そのあとです。

:::details 運用メモ — 観測指標
| 指標 | 見方 |
| --- | --- |
| 初動時間 | 通知 → 証拠パッケージ完成まで |
| パッケージ利用率 | インシデントで JSON を参照したか（手動クエリ再実行率の逆） |
| LLM 案の採用率 | レポート案のうちそのまま使った段落の割合（定性で可） |
| CI ルール阻止数 | 構文木側が実際に止めた PR 数 |
| SLI ベースライン | 4種が暫定集計で取れているか |
| 脆弱性対応期限 | Critical/High が 5営業日以内に処理開始されたか |
:::
